# Hera v2: build plan (EVM + Stellar compliance)

Status: draft for review · Owner: engineering · Last updated: 2026-10-18

Hera is a compliance layer for teams that move value on **Stellar** and **EVM chains**. It covers wallet monitoring, KYT (Know Your Transaction), AML risk scoring, sanctions screening and the Travel Rule. We build all of it ourselves: our own chain ingestion, our own label set, our own scoring. We do not resell Chainalysis, TRM, Elliptic or any other intelligence vendor.

This document covers:

1. Product scope and how it maps to the two plans

## 2. The identity model

Most compliance tools key everything on a bare address string. That is the root cause of the Stellar bugs described in `Working with Stellar`. On Stellar a single `G…` address often stands for thousands of customers at an exchange or anchor, and the real counterparty is identified by a **muxed ID** (SEP-23) or a **memo**.

So every subject in Hera is a structured reference, never a string:

```ts
type SubjectRef =
  | { chain: "stellar"; account: string /* G… */; sub?: { kind: "muxed"; id: bigint } | { kind: "memo"; type: "id" | "text" | "hash"; value: string } }
  | { chain: `evm:${number}`; address: `0x${string}` /* EIP-55 checksummed */ };
```

Rules that follow from this:

- **Decode on ingest, not on display.** An `M…` address is decoded into `{account, muxed id}` the moment it enters the system (API input, chain ingestion, CSV import). The original strkey is kept for display.
- **Screening uses both levels.** A `G…` base account can be clean while one sub-account under it is flagged, and the reverse. Scores are stored for the base account and for each `(account, sub)` pair.
- **Every downstream record carries the full `SubjectRef`.** That includes alerts, cases, Travel Rule messages and audit entries. The sub-identity is never flattened away.
- **EVM addresses are stored checksummed.** Input is validated with EIP-55, and mixed-case input with a bad checksum is rejected, because it usually means a typo.
- **Memo semantics are configurable per counterparty.** For a known exchange, `memo id` = customer routing. For unknown accounts a memo is kept as context but not treated as identity.

This is implemented in `packages/core/src/stellar/strkey.ts` (SEP-23 codec with CRC16-XModem, tested against vectors generated by the reference Stellar SDK) and `packages/core/src/evm/address.ts` (EIP-55). Web and API both use them.

## 3. Architecture and tech stack

One language end to end: **TypeScript**. The web app, the API, the ingestion workers and the SDK all import the same compliance engine from `packages/core`, so a muxed-account decode, a risk reason code or an IVMS101 type means exactly the same thing everywhere.

```
hera/                          pnpm workspaces + Turborepo
├─ apps/web        Next.js 16 (App Router)  ── marketing site + dashboard
├─ apps/api        NestJS 11                ── REST API, auth, screening, workers
├─ packages/core   @hera/core               ── strkey/SEP-23, EIP-55, SubjectRef,
│                                              chain adapters, risk engine,
│                                              Travel Rule thresholds + IVMS101
└─ docs/
```

```
  Stellar (Horizon → RPC/Galexie) ─┐          ┌─ EVM (Blockscout → own nodes)
                                   ▼          ▼
                        ┌──────────────────────────────┐
                        │ apps/api  (NestJS)           │
                        │  ├ ingest workers (BullMQ)   │  normalized Transfer events
                        │  ├ screening + risk engine   │◀── @hera/core
                        │  ├ alerts / rules            │
                        │  ├ travel-rule               │
                        │  └ auth, orgs, keys, audit   │
                        └──────┬───────────────┬───────┘
                               ▼               ▼
                        ┌────────────┐   ┌────────────┐
                        │ Postgres   │   │ Redis      │  queues, rate limits,
                        │ (Drizzle)  │   │            │  hot score cache
                        └────────────┘   └────────────┘
```

## 4. Chain ingestion

Both ingesters emit the same normalized event, so everything downstream is chain-agnostic:

```ts
interface Transfer {
  id: string;                 // chain-unique: tx hash + op index / log index / trace path
  chain: "stellar" | `evm:${number}`;
  txHash: string;
  ledgerOrBlock: number;
  timestamp: string;
  kind: "payment" | "path_payment" | "create_account" | "merge" | "claim" | "clawback"
      | "native" | "erc20" | "erc721" | "erc1155" | "contract_token";
  from: SubjectRef;
  to: SubjectRef;
  asset: { code: string; issuerOrContract?: string; decimals: number };
  amount: string;             // decimal string, never float
  usdValue?: string;          // priced at block time
  memo?: { type: string; value: string };
  successful: boolean;
}
```

### Stellar

- **Source:** Horizon for phase 1 (it is what the current adapter in `@hera/core` uses). Then Stellar RPC `getLedgers` for the live tip and Galexie ledger-meta exports for history and backfill. If TypeScript XDR decoding of full ledger meta becomes a bottleneck, this one worker can move to Go and the official `stellar/go` ingest SDK without touching anything else, because it only has to emit `Transfer` events.
- **Operations mapped:** `payment`, `path_payment_strict_send` / `_receive` (record both source asset and destination asset), `create_account`, `account_merge`, `create_claimable_balance` / `claim_claimable_balance` (the transfer happens at claim time), `clawback`, `clawback_claimable_balance`, `set_trust_line_flags` (authorization revocations are a compliance signal), plus Soroban token events (SAC and SEP-41 `transfer` / `mint` / `burn` / `clawback`).
- **Muxed accounts:** decode `M…` source and destination at ingest (section 2). Transactions with a muxed fee source are handled the same way.
- **Memos:** captured at transaction level and attached to every Transfer in that transaction.
- **Anchor attribution (SEP-1):** crawl `home_domain` for every account that sets one, fetch `/.well-known/stellar.toml`, and record `ORG_NAME`, `SIGNING_KEY`, `CURRENCIES` issuers and SEP endpoints (`WEB_AUTH_ENDPOINT`, `KYC_SERVER`, `TRANSFER_SERVER`, `DIRECT_PAYMENT_SERVER`). An account is only attributed to an org if the toml lists it back, which prevents spoofing by setting someone else's domain.
- **Spam filtering:** dust payments (e.g. 0.0000001 XLM) are stored but excluded from exposure maths.

### EVM

- **Source:** phase 1 reads Blockscout's open API (open source, so we can self-host it). Phase 2 moves to our own nodes for Ethereum (Reth) and providers for L2s, read with `viem`. Ingest by block with a reorg buffer (finalized-minus-N for scoring, tip for "pending" alerts).
- **Native value:** from `trace_block` / `debug_traceBlockByNumber` (call traces), not just top-level `tx.value`. Internal transfers from contracts (e.g. mixer withdrawals) are only visible this way.
- **Tokens:** `Transfer(address,address,uint256)` for ERC-20 / 721, `TransferSingle` / `TransferBatch` for 1155. Token metadata is cached per contract.
- **Issuer freeze signals:** index stablecoin freeze events (USDT `AddedBlackList`, USDC `Blacklisted`). An address frozen by an issuer is a strong first-party signal that we observe directly on-chain.
- **Account abstraction:** decode ERC-4337 `UserOperationEvent` so the smart-account sender is the subject, not the bundler.

## 5. Building our own intelligence

This is the moat, and it is the part people usually buy. We build it in layers, each with explicit **provenance** (every label records source, date and confidence) so an analyst can always answer "why did Hera say this?".

### 5.1 Label sources (all first-party or public-record)

| Source | What we get | Refresh |
|---|---|---|
| OFAC SDN list (XML, "Digital Currency Address" fields) | Sanctioned addresses: ETH, XLM, USDT, USDC, etc. | Hourly poll, diff, alert on new matches against all watched wallets |
| UN, EU, UK OFSI consolidated lists | Sanctioned entities and names (used for Travel Rule name screening) | Daily |
| Stellar SEP-1 tomls (section 4) | Anchors, issuers, exchanges and their signing keys | Daily crawl |
| On-chain issuer actions | USDT / USDC freezes, Stellar trustline authorization revocations, clawbacks | Real time |
| Contract metadata | Verified source, bytecode similarity to known mixers / drainers / bridges | On first sight |
| Public incident reports | Exploit and hack addresses with references | Analyst-curated |
| Customer and consortium labels | Exchanges labelling their own deposit wallets; confirmed fraud reports from customers | Real time, opt-in, weighted by reporter trust |

### 5.2 Clustering (phase 3)

- **EVM deposit-address heuristic:** addresses that receive from many senders and sweep to one known exchange hot wallet are attributed to that exchange.
- **Stellar custodial detection:** heavy muxed or memo-ID inbound usage plus a toml back-reference marks an omnibus account.
- **Contract-deployer clustering:** contracts deployed by the same EOA inherit a weak link.

### 5.3 Risk scoring

The score is 0–100 and **always comes with its reasons**. A score without an explanation is useless to a compliance officer.

```
categorySeverity: sanctions=100, terrorist_financing=100, stolen_funds=90, ransomware=90,
                  darknet=85, mixer=75, scam=70, gambling=40, high_risk_exchange=50,
                  bridge=10, exchange=5, anchor=5, defi=10

direct      = max(severity[c]) over categories the subject itself carries
exposure(c) = Σ value received from category c at hop h × decay(h)
              decay(1)=1.0, decay(2)=0.5, decay(3)=0.25, stop at 3 hops
indirect    = max over c of severity[c] × min(1, exposure(c) / totalInbound × k)
behavior    = Σ fired behavior rules (structuring, rapid in-out, peel chain, fresh account, dormant reactivation), capped at 30

score = clamp(max(direct, indirect, behavior + baseline), 0, 100)
band  = 0–24 low · 25–49 medium · 50–74 high · 75–100 severe
```

Any direct sanctions hit forces the score to 100 and the decision to `block`, whatever else is true.

The phase 1 version of this engine (direct exposure, first-hop counterparty exposure and behavior signals) is in `packages/core/src/risk.ts`, with tests. The API runs it server-side against live Horizon and Blockscout data. Multi-hop exposure plugs in behind the same reason codes in phase 2, so the UI and SDK won't change.

## 6. KYT: rules and alerts

- **Pre-transaction (sync):** `POST /v1/screen` with `{subject, direction, asset, amount}` returns `{decision: allow | review | block, score, reasons[]}`. This is what a wallet or exchange calls before signing or crediting.
- **Post-transaction (async):** every transfer touching a watched wallet is scored, and a rule match creates an alert plus a webhook.
- **Rules** are JSON, versioned per org, with dry-run against the last 30 days before they are enabled:

```json
{ "id": "high-value-unhosted", "when": { "all": [
    { "fact": "amount_usd", "op": "gte", "value": 10000 },
    { "fact": "counterparty.hosted", "op": "eq", "value": false } ] },
  "then": { "severity": "high", "action": "review" } }
```

- **Built-in rule pack:** sanctions hit, exposure above threshold per category, structuring (several just-below-threshold transfers within 24 h), rapid in-out (more than 90 % of inbound leaves within 1 h), first interaction with a high-risk counterparty, Travel Rule missing above jurisdiction threshold, Stellar: payment to a shared account without the expected memo or muxed ID.
- **Alert lifecycle:** `open → in_review → escalated → closed (true_positive | false_positive)`. Closing requires a note. Dispositions feed back into rule tuning.

## 7. Travel Rule

### Data model

**IVMS101** is the common payload. Hera stores originator and beneficiary as IVMS101 JSON and validates it with a schema.

Minimum fields for a compliant send:

- **Originator:** natural or legal person name, account number (address plus muxed ID or memo on Stellar), and one of: geographic address, national ID, customer ID, or date and place of birth.
- **Beneficiary:** name and account number.
- **VASPs:** originating and beneficiary VASP legal name, plus LEI where one exists.

### Thresholds

Configurable per org. Defaults ship as data, not code, and must be reviewed with counsel before go-live.

| Jurisdiction | Threshold | Note |
|---|---|---|
| FATF baseline | USD/EUR 1,000 | Recommendation 16 |
| United States | USD 3,000 | FinCEN, 31 CFR 1010.410(f) |
| European Union | EUR 0 | TFR (EU) 2023/1113, in force since 30 Dec 2024. Self-hosted wallet transfers above EUR 1,000 need ownership verification. |
| United Kingdom | EUR 1,000 for full data | Reduced data below |
| Singapore | SGD 1,500 | MAS PSN02 |
| Canada | CAD 1,000 | |

### Protocol strategy

1. **Hera ↔ Hera network (phase 2).** When both VASPs use Hera, exchange is direct: signed, encrypted IVMS101 over HTTPS, with ack and accept/reject. This is fast to ship and solves the network effect inside our own customer base first.
2. **Stellar-native discovery.** For a Stellar destination, find the beneficiary VASP from the destination account's `home_domain` and its verified stellar.toml. For anchors using SEP-31, the receiving anchor's SEP-12 KYC requirements already define what sender and receiver data it needs, so Hera maps IVMS101 to and from SEP-9 fields. There is **no ratified SEP field for a Travel Rule endpoint**. Until there is one, we publish our endpoint in the toml under a Hera-namespaced key and propose a SEP with the community.
3. **TRP (OpenVASP Travel Rule Protocol) interop (phase 3),** then TRISA. This covers counterparties that do not use Hera.
4. **Unhosted wallets.** Require proof of control by message signature: SEP-10-style challenge on Stellar, EIP-191 / EIP-712 signature on EVM. Store the proof with the transfer.

### Transfer lifecycle

```
draft → awaiting_counterparty → acknowledged → accepted → settled
                              ↘ rejected
               (no VASP found) → unhosted_verification → verified → settled
```

Names on both sides are screened against sanctions lists with fuzzy matching (Jaro-Winkler plus transliteration) before the message is sent.

## 8. Compliance audit reports (PDF)

Regulators, auditors, banking partners and a customer's own compliance officer all ask the same thing: *show me*. Hera turns its records into signed, regulator-ready PDFs, each with a machine-readable JSON twin.

### 8.1 Report types

| Report | Scope | Who asks for it | Contents |
|---|---|---|---|
| **Screening evidence** | One subject, one moment | Analyst closing an alert, a bank asking about a counterparty | Subject with decoded identity (muxed ID or memo), score, band, decision, every reason with its points and label provenance, counterparties, the transfers that were scored, data sources, engine version, timestamp |
| **Compliance audit report** | Whole org, date range (month / quarter / custom) | External auditor, regulator, board | Executive summary; screening volume by chain and risk band; alerts opened, closed and escalated, with dispositions and time-to-decision; Travel Rule transfers by jurisdiction and status (including unhosted-wallet verifications); watched wallets; rule and threshold changes; user and API key access changes; **audit-log chain verification result**; methodology appendix (scoring model, label sources, thresholds in force) |
| **Travel Rule record** | One transfer | Counterparty VASP, regulator request | IVMS101 originator and beneficiary, VASPs, threshold check and the rule that applied, status timeline with actors, proof of wallet control for unhosted wallets |
| **Case file** (phase 2) | One case | SAR/STR preparation | Alerts, notes, dispositions and evidence reports bundled in one document |

### 8.2 Integrity

A PDF that can be edited after the fact is worthless as evidence.

- Every report gets an ID (`RPT-…`) and is generated from a **frozen JSON snapshot**, stored next to the PDF.
- The SHA-256 of the canonical JSON and of the PDF are printed in the footer of every page, stored in Postgres, and written to the hash-chained audit log (`report.generated`).
- `GET /v1/reports/verify?sha256=…` (public, rate-limited) tells anyone holding a copy whether it is genuine and unaltered, and which org issued it, without exposing its contents.
- Phase 2: an Ed25519 signature over the JSON hash with a per-org key (KMS), embedded in the PDF metadata. Phase 3: PAdES-compliant PDF signatures for EU auditors.
- Reports are immutable. Regenerating creates a new report that references the old one.

### 8.3 How it's built

- **Rendering:** `@react-pdf/renderer` inside the NestJS API, with JSX templates in `apps/api/src/reports/templates`. It is deterministic, needs no headless browser, embeds the brand fonts, and uses the same paper-and-ink design as the app in a print-safe palette (no hard shadows, AA contrast on white).
- **Jobs:** small reports (evidence, Travel Rule record) render synchronously in under 2 s. Org-wide audit reports run as BullMQ jobs: `queued → rendering → ready | failed`, with a notification when ready.
- **Storage:** S3 (or the local `.data/` folder in dev), with object-lock retention matching the org's record-keeping period (default 5 years, the FATF minimum).
- **Data rules:** reports render only from data the requester's role can see. IVMS101 PII appears only in Travel Rule records and case files, never in the org-wide audit report, which shows counts.

### 8.4 API and UI

```
POST /v1/reports            { type: "screening_evidence" | "audit" | "travel_rule", params }
GET  /v1/reports            list, with status
GET  /v1/reports/{id}       metadata + hashes
GET  /v1/reports/{id}/pdf   the document
GET  /v1/reports/{id}/json  the frozen snapshot
GET  /v1/reports/verify?sha256=…
```

- `/app/reports`: generate an audit report (pick a range), see history, download, copy the verification link.
- One-click **Export evidence** on every screening, alert and Travel Rule transfer.

### 8.5 Phasing

- **Phase 1:** screening evidence PDF and Travel Rule record PDF, with hashes and the verify endpoint.
- **Phase 2:** org-wide compliance audit report, scheduled monthly delivery by email, case files, and per-org signatures.
- **Phase 3:** PAdES signatures, plus regulator-specific exports (FinCEN SAR, goAML XML) alongside the PDF.

## 9. Auth, tenancy and security

- **Accounts:** email and password (argon2id), email verification, password reset, optional TOTP 2FA (required for Owner and Admin). Enterprise adds SAML / OIDC SSO with SCIM.
- **Sessions:** opaque random token in an `HttpOnly; Secure; SameSite=Lax` cookie. Only its SHA-256 hash is stored, in the `sessions` table (moving to Redis when needed). Mutations require `Content-Type: application/json`, which together with SameSite blocks cross-site form posts. **No API keys or session tokens in `localStorage`.**
- **Tenancy:** every row has `org_id`, enforced by Postgres row-level security and by the API layer.
- **RBAC:** Owner, Admin, Analyst, Viewer. Analysts can disposition alerts. Only Admins can change rules or keys.
- **API keys:** `hera_live_<prefix>_<secret>`. Only an HMAC of the secret is stored; it is shown once. Keys are scoped (read, screen, travel_rule) and can be restricted by IP allowlist.
- **Webhooks:** signed with `Hera-Signature: t=<ts>,v1=<HMAC-SHA256>`, retried with backoff for up to 24 h, replayable from the dashboard.
- **Audit log:** append-only, hash-chained (each entry stores the hash of the previous one), exportable. Covers logins, key changes, rule changes and alert dispositions.
- **Compliance of our own:** SOC 2 Type I in phase 3, encryption at rest for PII (IVMS101 payloads are field-level encrypted with per-org keys via KMS), EU data residency option.

Current repo issues fixed on this branch:

- `api/auth/login.js` shipped hardcoded fallback credentials and returned an upstream API key to the browser.
- `api/hera/[...path].js` proxied to any URL passed in a request header (an open relay).

Both are removed.

## 10. API, SDK and webhooks

REST, versioned under `/v1`, with an OpenAPI 3.1 spec that generates the SDKs.

```
POST /v1/auth/signup | /login | /logout     GET /v1/auth/me
POST /v1/screen                              # sync pre-transaction screening (today: subject only;
                                             #  phase 1 adds optional direction/asset/amount)
GET  /v1/subjects/{chain}/{address}          # profile + score + reasons
POST /v1/wallets   GET /v1/wallets           # watchlist (monitoring)
GET  /v1/transfers?wallet=…                  # normalized activity
GET  /v1/alerts    PATCH /v1/alerts/{id}
POST /v1/travel-rule/transfers               # create + send IVMS101
GET  /v1/travel-rule/transfers/{id}
POST /v1/rules     POST /v1/rules/{id}/dry-run
GET  /v1/audit-log
```

SDK example:

```ts
import { Hera } from "@hera/sdk";
const hera = new Hera({ apiKey: process.env.HERA_API_KEY });

const result = await hera.screen({
  subject: "MA5ZSEJYB37JRC5AVCIA5MOP4RHTM335X2KGX3IHOJAPP5RE34K4KAAAAAAAAAAAFJOYK", // muxed: decoded for you
  direction: "outbound", asset: "USDC", amount: "2500", // phase 1: feeds amount-based rules
});
if (result.decision === "block") throw new Error(result.reasons[0].message);
```

## 11. Redesign

The current site reads as a dark, generic "crypto infra" template. Compliance software usually looks either intimidating or dull. Hera should feel like the friendly expert in the room: confident, specific, a little playful, and never vague about what it found.

### 11.1 Brand idea

**Argus the peacock.** In the myth, Hera set the hundred eyes of Argus, her all-seeing watchman, on the peacock's tail. Hera, the product, puts those eyes on your transactions. Argus is the mascot. His tail feathers are eyes that blink and track, and he reacts to results: calm on `low`, alert on `high`, feathers up on `severe`.

### 11.2 Visual system

| Token | Light | Dark | Use |
|---|---|---|---|
| `paper` | `#FFF5E8` | `#16120E` | Page background (warm, not white) |
| `card` | `#FFFFFF` | `#211B15` | Surfaces |
| `ink` | `#17130F` | `#FFF5E8` | Text, **2px outlines on every surface**, hard shadows |
| `sun` | `#FFC93C` | same | Primary CTA fill, highlights |
| `peacock` | `#0F9D8A` | `#2CC7B1` | Brand, "clear" state, Stellar accents |
| `iris` | `#4B5BFF` | `#7D8BFF` | Links, EVM accents, focus |
| `blush` | `#FF8FB8` | same | Playful accents, Travel Rule |
| `risk-low/med/high/severe` | `#22A06B` / `#F5A524` / `#FF6B3D` / `#E5372B` | brighter variants | Risk bands only. Never decorative. |

- **Type:** Bricolage Grotesque (display, 600–800), DM Sans (UI and body), DM Mono (addresses, hashes, amounts, code).
- **Shape:** 2px ink borders, 14px radius on cards and 10px on controls, and hard offset shadows (`4px 4px 0 ink`) that collapse to `0 0` when a button is pressed, so clicks feel physical.
- **Texture:** faint dot grid on paper; "stamp" badges (CLEAR, REVIEW, BLOCKED) that rotate in like a rubber stamp.
- **Motion** (Motion for React): springy entrances (stiffness 260, damping 20), staggered lists, a stamp slam for verdicts, a marquee of supported assets, Argus idle blink every 4–6 s. Everything respects `prefers-reduced-motion`.
- **Accessibility:** WCAG AA contrast for text on paper and on sun, visible 3px focus rings in `iris`, risk bands always shown as text and icon, never color alone.

### 11.3 Information architecture

**Marketing (`apps/web/app/(marketing)`):**

Then trusted-by and asset marquee, "How it works" (Watch → Score → Act), Stellar depth (muxed, memos, SEPs), EVM depth, Travel Rule, the SDK snippet, pricing (Developer / Enterprise), FAQ and a final CTA.
- `/pricing`, `/stellar` (the "Working with Stellar" guide as a designed page), `/docs` (quick start).

**Auth (`app/(auth)`):** `/signup` (name, work email, company, password, plan), `/login`, `/forgot-password`. Split layout: form on the left, Argus and a rotating fact on the right.

**App (`app/(app)/app/...`):**
